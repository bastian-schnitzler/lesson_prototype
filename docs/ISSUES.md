## Ongoing GitHub synchronization

Once these issues are published, every change to `docs/SPEC.md` or `docs/ISSUES.md` must also refresh GitHub issues in the same change workflow. Update affected titles, scope, acceptance criteria, dependencies, Mermaid diagrams, matching PlantUML source fences, and server-rendered preview URLs, and refresh specification version/commit links across the published backlog. Preserve issue numbers/URLs and record mappings for new issues. Verify the remote updates before reporting the change complete; explicitly report pending synchronization if GitHub access is unavailable. See [the specification's synchronization rule](SPEC.md#keep-github-issues-synchronized).

## GitHub titles and milestones

Use each issue heading below as its GitHub title, including the phase/issue prefix and colon: `P0-01: Create and refine the lesson prototype specification`, etc. The title prefix is the logical roadmap ID; GitHub assigns a separate repository issue number for links; branch names use the logical ID. Existing published issue numbers/URLs stay stable when their titles or scope change.

Create or reuse milestones named exactly **Phase 0**, **Phase 1**, **Phase 2**, **Phase 3**, **Phase 4**, **Phase 5**, and **Phase 6**. Each phase's issues must be assigned to that milestone, with its description based on the corresponding SPEC deliverables and exit criteria. Check for existing milestones before creating them and verify every issue's assignment. The phase 4 backlog was defined in P4-01; phase 5 review and closing tasks remain requirements-dependent, and its detailed implementation backlog follows later.

Each implementation phase ends with a dedicated issue to improve its Salt mockups against the actual running prototype. That mockup-refresh issue is always the **last issue of its milestone**: it has the highest logical ID in its phase and depends, directly or transitively, on every other issue of that phase. When an issue is added to a phase, renumber so the mockup issue stays last; GitHub issue numbers do not change. Compare the real pages against the SPEC visual contract and supplied screenshot references R1–R5, update sources and their matching embedded PlantUML code fences, update the single mockup README and documentation links, and synchronize published GitHub issue assets. These closing issues are part of phase completion.

## Makefile workflow

Create the Makefile in **P1-01**, then use Make targets for every workflow task. Recipes may call package-manager/Node/test tools internally; documentation and CI invoke make. Every subsequent issue adds or extends relevant targets and updates help. Use the [SPEC target table](SPEC.md#makefile-workflow) for generation, run/browser configuration, build, unit/integration/e2e/all tests, and mockup synchronization. Keep the source/Markdown parity check in test-all and CI. Function/reading review issues must plan the extension of existing generation/test targets when those categories become supported.

## Branch naming

Use the issue's logical ID from this file plus a short description: `P<phase>-<two-digit-issue>-<short-description>`, for example `P0-02-claude-spec-review` or `P1-01-build-lesson-index`. Keep the ID uppercase as in the heading; the description uses lowercase words separated by hyphens. The ID does not change at publication, so branch names never use GitHub issue numbers. The merged P0-01 branch `p0-01-create-spec` predates this rule. Before starting any issue, check the current branch: switch to the issue's branch if it exists, otherwise create it from the up-to-date main branch; never start issue work on `main` or another issue's branch.

### P2-05: Deliver formatted introduction and explanation text from generation

GitHub: [#52](https://github.com/bastian-schnitzler/lesson_prototype/issues/52).

Milestone: **Phase 2**.

Scope: vocabulary `vocabulary_introduction.text` and grammar `grammar_explanation.text` are currently unformatted plain text. They render as one dense paragraph in lessons and previews and are hard to read. The generating LLM should deliver this text already formatted, for example as Markdown, and the app should render the formatting. This issue starts with a short design brainstorm, records the decision in SPEC, then implements it and brings the existing briefs and lessons up to date.

Brainstorm (decide and record in SPEC before implementing):

- **Format options:**
  - (a) A restricted Markdown subset: paragraphs, line breaks, `**bold**`, `*italic*`, and bulleted or numbered lists. No headings, links, images, tables or raw HTML.
  - (b) Structured JSON blocks, such as `paragraph`, `list`, `tip` and `example`, with typed inline spans. These validate through the schema and need no parser, and Gemini structured output enforces them.
  - (c) A hybrid of the two.
  - Compare the options on LLM reliability, validation strength, locale parity across en/fr/de, diff readability in reviews, and rendering effort.
- **Learning-language spans:** decide how French forms inside explanations are marked, for example `{{fr:je suis}}` or a span type. Marked forms get `lang="fr"` for screen readers and fonts, consistent highlighting, and an optional Listen control. Decide whether bold alone may mark learning-language forms.
- **Rendering:** choose a small in-app renderer that produces React elements without `innerHTML`, or a vetted library with sanitising, and keep bundle size in mind.
  - Use it everywhere the text appears: `IntroductionRenderer`, `ExplanationRenderer`, Content previews (`ContentReview`), and the Draft `explanationPlan` if briefs adopt the format too.
  - Raw JSON stays unchanged.
  - Output must be semantic HTML (`p`, `ul`/`ol`, `strong`, `em`) in the dark design.
- **Validation:**
  - Allow only the chosen syntax.
  - Check structural parity across locales: the same number of paragraphs, list items and learning-language spans.
  - Set length limits per block.
  - Reject leftover plain-text artefacts such as `\n` literals or HTML.
  - Plain text must still be valid, or it fails with a clear diagnostic that names the item.
- **Scope of fields:** decide whether other learner-facing prose follows. Candidates are grammar `heading`, rule explanations, pitfalls, teaching notes, and brief `explanationPlan`/`coverageNotes`. Answer explanations probably stay plain.
- **Existing artifacts:**
  - Changing the schema or prompts changes the input hashes, so all existing lessons become stale.
  - Choose between three options:
    - A one-off migration script that wraps current text as single paragraphs. This is cheap, keeps the reviewed wording and adds no formatting.
    - Regeneration of content only with `make generate ID=<id> REGENERATE=1`. Briefs stay unless the decision extends formatting to them.
    - Hand-authoring the sample lessons, as in P1-08.
  - Consider ordering: if P2-04 has already generated the remaining 38 vocabulary lessons, all 48 vocabulary lessons and the 10 grammar samples are affected. Doing this before the P2-04 bulk generation avoids a second regeneration.
  - Regenerated or edited samples need a renewed content review before the bulk expansion (SPEC P1-08 review gate).

Decisions (2026-10-14, product owner):

- Design V2, the vertical timeline: one numbered circle per learning point in the colour of its start-page section. A point keeps its number when done (filled circle, no tick); the current point is ringed and says "You are here"; the exam has a flag and its task count.
- The sidebar is congruent with the start page: the start page lists the sections lettered A, B, C… (word groups, grammar blocks, function stages, the exercises, the exam), each with its learning points indented below and numbered as in the sidebar.
- Navigation only shows the way: there is no way back to earlier points, neither from the sidebar nor from the phone strip, and no Previous button. Locked submissions and scores are untouched by navigation.
- During the exam the sidebar lists the exam pages with their tasks and time limits, marks the current page and links nowhere.
- Phones: no drawer. - Results: the sidebar replaces the button menu; the final exam comes first with its parts (Translation/Dictation, or Translation/Replies/Dialogue) nested below, then the scored exercises. Only the selected part is shown. On phones the result parts stand above the answers.
